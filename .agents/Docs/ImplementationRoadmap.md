# 함락! 무한의 지옥철 현재 상태 및 실행 로드맵

작성 기준일: 2026-07-21

## 1. 문서의 역할

이 문서는 현재 저장소에 실제로 존재하는 구현과 앞으로 필요한 작업을 연결하는 실행용 로드맵이다.

- `Design.txt`: 최종 게임 규칙의 기준 문서
- `.agents/Docs/DevelopmentPlan.md`: 목표 구조, 개발 원칙과 장기 완료 기준
- `.agents/Docs/ImplementationRoadmap.md`: 현재 구현 상태, 미정 사항, 담당자와 다음 작업

`Design.txt`는 2026-07-14에 최신 논의와 동기화했다. `.agents/Docs/CardDataContract.md`는 정적 Lua 카드 DB, 구조화 효과 반환과 설명 속 태그 표기의 0단계 확정 계약으로 사용한다.

담당 표기는 다음 의미로 사용한다.

- 사용자: 게임 규칙의 최종 선택, 콘텐츠 원문, RisuAI 실제 환경 확인
- Codex: 구조 제안, 코드·데이터·템플릿 구현, 검증 도구와 기술 문서
- 공동: Codex가 선택지와 권장안을 제시하고 사용자가 최종 승인

## 2. 현재 상태 요약

현재 프로젝트는 **10장 드래프트와 단일 캐릭터 전투 수직 슬라이스가 로컬 계약 검사를 통과한 통합 프로토타입**이다. 카드 선택, 턴 판정, LLM 요청·출력 훅, 결과 확정과 동적 CBS UI가 코드상 연결되었다. 다만 실제 RisuAI 배포에서의 mode별 엔진 수명, 권한, 훅 순서와 렌더링 체감 지연은 아직 검증해야 한다.

지금 바로 24장의 카드나 모든 화면을 완성하면 규칙과 데이터 형식이 바뀔 때 대부분 다시 작성하게 된다. 우선 한 캐릭터와 소수 카드로 전투 수직 슬라이스를 완성한 뒤 드래프트, 보상, 도감과 전체 콘텐츠를 확장하는 것이 적절하다.

- `runtime-cache-check`, `runtime-bundle-contract-check`, `game-setup-incremental-check`, `ui-host-contract-check`이 warm/static 캐시, content revision, 71 seed·710 전이 동치와 UI slot 분리를 고정한다.
- 로컬 검사는 `lua` 명령이 없으면 설치된 Lua Language Server의 내장 호스트를 사용한다. 이는 실제 RisuAI 런타임 검사가 아니다.
- UI/LLM 없이 `turn_start`와 캐릭터 선택을 포함한 10턴 자동 시뮬레이터가 같은 시드의 전체 추적 재현성과 카드 보존을 검사한다.
- 파일을 실제 RisuAI 캐릭터·모듈의 로어북과 트리거에 반영하는 패키징 절차가 저장소에 없다.
- 캐릭터 첫 메시지는 `Prompt/firstmsg.html`에 정의되었고 외부 CBS가 아닌 상시 sentinel + `editDisplay`로 UI를 교체한다. 실제 host의 first-message index `-1`과 remount 동작은 배포 후 확인한다.
- 실제 RisuAI에서 팝업 기반이 현재 버전과 CSS 접두사 조건에서 정상 동작하는지 회귀 테스트가 필요하다.

## 4. 이미 결정된 목표

다음 항목은 다시 설계할 필요 없이 구현 계약으로 취급한다.

### 전투와 덱

- 캐릭터 저항을 0으로 만들면 승리한다.
- 플레이어 은폐가 0이 되거나 제한 턴 안에 승리하지 못하면 실패한다.
- 같은 해결 시점에 저항과 은폐가 모두 0 이하라면 승리를 우선한다.
- 플레이어와 캐릭터의 기본 드로우는 3장, 최대 손패는 5장이며 두 값은 캐릭터와 효과에 따라 별도로 달라질 수 있다.
- 턴 시작에는 기본 드로우 수만큼 최대 손패를 넘지 않게 드로우하고 턴 종료에 남은 손패를 버린다. 카드 효과의 드로우는 현재 턴에 즉시 적용한다.
- 세션 시작 덱과 버림 더미 재편성은 저장된 시드와 커서를 사용하는 결정적 셔플로 처리한다.
- 사용 카드는 턴 종료까지 별도 영역에 있어 같은 턴에 다시 뽑히지 않는다.
- 초기·최소 덱은 10장, 알파 최대 덱은 20장, 같은 카드는 최대 2장이다.
- 플레이어 퍽은 최대 3개다.

### 카드와 무드

- 모든 카드는 행동 태그 하나와 필요한 수의 메커니즘을 가진다.
- 초기 메커니즘은 `연계`, `제거`, `계획`, `간파`다.
- 엔진은 메커니즘 개수를 제한하지 않고 카드 설계에서 복잡도와 파워를 관리한다.
- 계획은 숨겨진 단일 슬롯을 사용하고 반드시 횟수·기간·만료 조건 중 하나 이상을 가진다.
- 계획 지속시간은 기본적으로 배치 턴을 세지 않는다. 카드가 `durationIncludesPlacementTurn = true`를 명시하면 배치 턴 종료부터 세며, `퇴로 봉쇄`는 이 설정으로 캐릭터가 행동하지 않은 배치 턴 종료에 만료된다.
- 계획 슬롯 점유와, 지속 턴이 있는 계획의 남은 지속 턴은 공개하고 남은 발동 횟수는 숨긴다.
- 발동한 계획의 정체는 슬롯에서 벗어날 때까지 공개하되 남은 발동 횟수는 계속 숨긴다.
- 발동하지 않고 만료되거나 교체된 계획은 공개하지 않는다.
- 미공개 계획의 카드별 묘사와 생각은 LLM 요청에도 넣지 않는다.
- 간파는 해당 카드 때문에 발동할 계획만 이번에 억제하며 계획을 공개하거나 충전을 소비하지 않는다.
- 무드는 `거절-의심-무시-혼란-순응`이다.
- 기본 무드 경계는 `5-4-4-5`, 공통 판정은 턴당 최대 한 단계다.
- 실제 직접 무드 변경이나 무드 고정이 발생한 턴에는 공통 무드 판정을 생략하고, clamp·동일값 no-op만으로는 생략하지 않는다.
- 같은 입력 사건의 트리거는 snapshot에서 수집해 계획 → 특징 → 퍽 → 환경, 행동 진영 → 상대 진영 → 소유자 없음, 안정 ID/index 순으로 해결한다.
- 마지막 허용 턴은 카드 행동을 모두 해결하고 승리가 아니면 gameplay `turn_end`와 공통 무드 전에 패배한다.

### 생성과 UI

- 사용자가 RisuAI 전송 버튼을 직접 누르는 것이 턴의 유일한 확정점이다.
- 별도 턴 종료 버튼은 두지 않으며 무선택 전송은 패스, 연계 카드만 등록한 전송은 연계 해결 후 패스다.
- 카드 상세는 native disclosure로 로컬에서 열고 닫으며, 명시 등록·취소 버튼만 token이 있는 controller action을 호출한다. 기존 두 번 클릭 focus/등록 흐름은 v1 저장·호환 경계로만 남긴다.
- 눈치보기는 권위 상태와 RNG를 바꾸지 않는 결정적 프리뷰로 현재 턴 1장을 보여주며 그 카드도 같은 턴 등록할 수 있다.
- 눈치보기와 원래 손패 카드는 함께 사용한다. 프리뷰 카드까지 등록한 뒤 다른 원래 손패 카드를 등록하면 speculative 가지를 취소하고 마지막 카드만 사용한다.
- 목표 UX에서는 입력창을 CSS로 입력할 수 없게 하고, 실제 문자열 편집 훅인 `editInput`에서도 입력을 정확한 filler로 정규화한다. 빈 전송 설정이 추가한 같은 `*says nothing*`은 제한된 `onStart` 준비·복구 경계에서 제거한다.
- Lua는 저수준 LLM 호출이나 자동 전송을 하지 않는다.
- 제한된 `onStart`에서 결과를 대기 트랜잭션으로 결정하고 `editRequest`에는 저장된 턴 사건만 추가한다. 자동 복구가 이미 관측된 출력의 commit만 마친 경우에는 새 LLM 요청을 취소한다.
- 프리셋, 캐릭터 설정과 로어북을 포함한 정상 요청을 유지한다.
- 정상 출력이 도착하면 `onOutput`에서 결과를 한 번만 반영하고 공개한다.
- 실패·재시도·재생성은 같은 `turnResult`를 사용한다.
- 전투 UI는 최신 출력 아래의 사용자 메시지 하나만 유지한다.
- 화면마다 `battleView`, `deckView`, `collectionView` 같은 구조화 채팅 변수 하나를 사용한다.
- 고정 정보는 `dict_element`, 가변 목록은 CBS 반복문으로 출력한다.
- 카드 설명의 `::tag[ASCII_ID]::` 토큰은 View에서 구조화된 조각으로 만들고 HTML/CBS가 스타일이 적용된 인라인 태그로 렌더링한다.
- 정적 게임 정의는 Lua 테이블, 진행 상태와 세이브는 함수 없는 JSON 직렬화 데이터로 관리한다.
- 카드 함수는 읽기 전용 컨텍스트에서 구조화된 효과를 반환하고 공통 엔진이 상태를 변경한다.

### 6.3 정상 생성 연결 전에 필요한 결정

| 미정 사항 | 담당 | 정해야 할 내용 |
|---|---|---|
| 빈 입력 전송 경로 | 완료(로컬 연결) | `editInput`은 전투 입력 문자열을 정확한 filler로 정규화하고, 빈 입력 UX와 제한된 `onStart`를 유지한다. `useSayNothing`이 자동 삽입한 같은 `*says nothing*`은 `onStart` 준비·복구 경계에서 제거한다. 최신 Risu가 사용자 공개 마커 뒤의 빈 전송에는 filler를 추가하지 않는 경우, 정확한 마커-only 상태를 같은 요청의 무출력 재시도로 처리한다. 전투 중 자동 계속은 끄고 수동 Continue·프롬프트 미리보기는 사용하지 않으며, 실제 재생성은 저장된 직전 pending을 재사용한다. 최신 웹 검증은 남아 있다. |
| 턴 사건 형식 | 완료(로컬 계약) | `TurnEventProjectionContract.md`와 strict 투영기로 행동·생각·결과 필드, 숨은 계획과 캐릭터 카드의 공개 경계를 확정. 실제 프롬프트 문장과 RisuAI 전달은 후속 연결 범위 |
| 기본 묘사 지침 | 완료(수직 슬라이스) | 기존 프리셋의 문체·길이·시점을 유지하고, formatter는 판정 준수·한 장면 구성·게임 시스템 용어 비노출에 필요한 최소 지침만 추가한다. |
| 생성 실패 UX | 완료(로컬 계약) | pending·RNG·공개 마커를 잠근 채 다음 빈 전송에서 재사용한다. 마커 뒤가 완전히 비었고 출력·정리 영수증이 없으면 채팅 변경 없이 attempt만 올려 재시도한다. chat anchor와 정리 영수증이 정확히 맞을 때만 미관측 부분 응답을 자동 삭제하고, `onOutput`이 관측한 응답은 보존한 채 commit만 재개한다. 위변조·불명확한 suffix는 삭제하지 않는다. 실제 경고 문구, Continue 금지와 생성 중 전송 직렬성은 통합 검사에서 확인한다. |
| 출력 재생성 | 완료(직전 턴 범위) | 공개 턴 번호의 사용자 메시지와 저장된 직전 pending을 연결한다. 직전 출력의 실제 재생성은 같은 판정과 LLM 사건을 재사용하고 권위 상태는 중복 반영하지 않는다. 과거 여러 턴의 임의 재생성은 수직 슬라이스 범위에서 지원하지 않는다. |

### 1단계: RisuAI 연결 원칙 확인

상태: 완료. 최신 웹 버전을 사용하고 `main.lua`만 트리거 스크립트이며, 나머지 Lua 스크립트·정적 DB(`.db`)·HTML 파일은 각각 별도 로어북으로 등록되는 구성을 확인했다.

독립된 임시 런타임이나 진단 계층은 만들지 않는다. 실제 전투 모듈이 준비되기 전에 빈 이벤트 중계 구조를 추가하면 검증 뒤 다시 제거하거나 `main.lua`를 반복 수정해야 하기 때문이다.

확정된 원칙:

- 캐릭터의 서술용 첫 메시지는 현재 구현의 선행 조건이 아니며 후속 단계에서 정한다.
- 초기 UI 생성 시점은 실제 전투 연결 단계에서 함께 검증한다.
- `System/main.lua`는 변경할 때마다 정확한 diff를 먼저 제시하고, 해당 변경 건에 대한 사용자 승인을 받은 뒤 수정한다.
- 훅 순서, 초기화 수명, 프리셋 유지와 UI 메시지 교체는 실제 전투 모듈을 연결할 때 함께 검증한다.
- Lua가 `LLM` 또는 `simpleLLM`을 직접 호출하지 않는 원칙은 유지한다.

사용자 작업:

- 프리셋별 묘사 품질 확인
- 기본 묘사 지침과 카드별 문구 조정
- 실패·재시도 UX가 이해 가능한지 실제 사용 확인

완료 기준:

- 최소 3턴을 연속으로 수동 전송해 플레이할 수 있음
- 캐릭터 행동과 결과는 출력 전 공개되지 않음
- 프리셋과 로어북이 정상적으로 적용됨
- 재시도해도 같은 턴이 다시 계산되거나 중복 반영되지 않음

### 6단계: 고정 구성 한 세션 완주

목표는 드래프트와 보상 없이 고정 덱·고정 캐릭터로 승패까지 플레이하는 것이다.

Codex 작업:

- 세션 시작, 제한 턴, 환경과 시작 효과 연결
- 저항 0, 은폐 0과 턴 소진의 종료 처리
- 세션 로그와 결과 화면 구현
- 새 세션 전 상태 정리 구현

사용자 작업:

- 최소 콘텐츠 수치의 1차 밸런스 조정
- 한 장면의 길이와 전체 세션 플레이 시간 평가
- 승리·실패 결과 문구 제공

완료 기준:

- 한 세션을 시작부터 승리 또는 실패까지 중단 없이 완료함
- 일반적인 세션 길이와 LLM 묘사량이 의도와 맞는지 판단할 로그가 있음

### 7단계: 덱빌딩과 반복 세션

목표는 이 게임의 핵심 메타 루프인 드래프트, 대상 선택, 보상과 다음 세션을 연결하는 것이다.

Codex 작업:

- 완료(로컬): 10회 초기 카드 드래프트, 재현 검증과 정적 shell 캐시
- 캐릭터 후보 3명 생성과 상성 정보 View 구현
- 보상 4종과 덱·퍽 교체 제한 구현
- 덱 10~20장, 동일 카드 2장, 퍽 3개 제한 구현
- 다음 세션으로 영구 상태 연결

사용자 작업:

- 전체 루프 검증용 카드·캐릭터·퍽·환경 콘텐츠 제공
- 드래프트 및 보상 출현 규칙 승인
- 캐릭터 후보에게 공개할 정보와 난이도 문구 작성

완료 기준:

- 새 게임부터 두 번째 세션 시작까지 끊김 없이 진행됨
- 덱과 퍽 제한을 우회할 수 없음
- 선택지가 덱 구성에 의미 있는 영향을 줌

### 8단계: 보조 화면 데이터 연결

목표는 현재 목업인 덱, 도감, 프로필, 가이드와 설정을 실제 상태에 연결하는 것이다.

Codex 작업:

- `deckView`, `collectionView`, `profileView`, `settingsView` 구현
- 모든 가변 목록을 CBS 반복문으로 전환
- 팝업 필터, 정렬, 뒤로가기와 빈 상태 구현
- 판타지 임시 콘텐츠와 존재하지 않는 이미지 참조 제거

사용자 작업:

- 도감 분류와 해금 문구 제공
- 캐릭터 프로필의 공개·비공개 범위 결정
- 실제 플레이 가이드 원문과 설정 항목 확정
- 최종 이미지와 캐릭터 초상 제공 또는 제작 방향 결정

완료 기준:

- 모든 보조 화면이 DB와 저장 상태를 표시함
- 하드코딩된 카드·캐릭터 데이터가 남아 있지 않음
- 잠긴 정보가 UI에서 유출되지 않음

### 9단계: 알파 콘텐츠와 밸런스

목표는 수직 슬라이스를 콘텐츠 규모가 있는 알파로 확장하는 것이다.

Codex 작업:

- 콘텐츠 일괄 검증과 누락 보고
- 플레이 로그 집계와 밸런스 지표 구현
- 대표 메커니즘 조합 회귀 테스트
- 모바일·데스크톱 UI 최종 검증

사용자 작업:

- 알파 목표 수량의 콘텐츠 완성
- 플레이 로그를 바탕으로 수치, 카드 풀과 캐릭터 덱 조정
- 최종 문체와 콘텐츠 표현 검수

완료 기준은 `.agents/Docs/DevelopmentPlan.md`의 알파 완료 기준을 모두 만족하는 것이다.

## 10. 당분간 하지 않을 작업

- 24장 전체 카드 작성
- 세 캐릭터의 완성형 스토리와 일러스트 제작
- 도감과 설정 화면의 세부 기능 구현
- 드래프트 희귀도와 장기 밸런스 미세 조정
- 전투 목업의 시각 효과 추가
- 현재 정적 HTML을 모두 한꺼번에 동적 템플릿으로 변환

이 작업들은 수직 슬라이스에서 데이터 계약, 턴 처리와 정상 생성 흐름이 검증된 뒤 진행한다.

## 11. 진행 상태 갱신 규칙

각 단계가 끝날 때 이 문서의 구현 현황과 미정 사항을 갱신한다.

- 규칙이 결정되면 미정 표에서 제거하고 `Design.txt`에 반영한다.
- 코드가 작성되었다는 이유만으로 완료 처리하지 않고 해당 단계의 완료 기준을 실제 RisuAI에서 검증한다.
- 임시 콘텐츠는 ID와 목적을 명시해 최종 콘텐츠와 구분한다.
- 새 기능이 필요해도 현재 수직 슬라이스의 완료를 막지 않으면 후속 단계로 보낸다.
- 사용자 결정이 필요한 작업은 구현 직전에 선택지와 권장안을 다시 제시한다.
